> 📌 **后来的变化(0.4.0 起)**:发版收成了一条命令 —— `bash tools/release.sh`。
> 它连版本号推导和 CHANGELOG 都做了。本文下面写的三步手工流程已不再是推荐路径,
> 保留是因为它记录了 0.3.0 当时的形态。当前流程见
> [docs/06](../../docs/06-app-conventions.md#发版流程)。

发版这件事本身交给 CI 了:**推一个 tag,剩下全部自动**。

以前发版是本地一条条跑:`tag-release.sh` 打 tag → 手工写 Release 说明 → `gh release create` → `release-apk.sh --upload`。现在只剩第一步。

---

## 新的发版流程

```bash
bash tools/tag-release.sh --bump minor     # 涨版本
git commit -am "chore(release): 0.3.0" && git push
bash tools/tag-release.sh                  # 打 tag 并推送
```

推完 tag,CI 自动:

```
校验 tag 与 version.properties 一致
还原签名凭据(secret KEYSTORE_B64)
从 tag 构建 assembleRelease
逐个校验:已签名 / versionName==tag / versionCode==推导值 / 非 debuggable / 无 debug 钩子
建 Release + 挂上 APK
```

> 签名凭据没配的话 CI **直接失败**,而不是降级发一个 unsigned 包 —— 那种包装不上设备,
> 发出去只会浪费别人的时间。`ci.yml` 里的降级为警告是另一回事,那里只是编译检查。

## 这个 Release 的说明是手写的

`docs/releases/0.3.0.md` 就是本文件。CI 会把它放在开头,再接上自动生成的部分:

- 附件表(文件名 + 大小)
- **签名证书 SHA-256** —— 下载后可以核对「这和已装的是不是同一个应用」
- 安装命令(Pico / TCL 电视两条路)
- `<上一个 tag>..0.3.0` 的变更列表
- 「包来自 tag 检出而非工作区」的声明

不想手写就不写,CI 会自己拼一份完整的。约定见 [`docs/releases/README.md`](../README.md)。

## 本版还顺手修了一处文档错误

`docs/06` 里第二次把发版命令写成 `bash tools/tag-release.sh <version>` —— 这个脚本**不接受版本参数**,版本取自 `version.properties`。已修,并加了复查命令确认全仓库没有这种写法了。

> 同一个错犯两次,说明「脚本参数」这种东西光靠记是不行的。这次的复查命令留在了提交说明里。
